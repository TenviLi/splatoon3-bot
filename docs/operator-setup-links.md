# Operator Setup Links

Checked against current first-party documentation on 2026-08-01. Store every YAML configuration described below as a GitHub **Repository Secret** under **Settings → Secrets and variables → Actions**. Do not commit real credentials, tokens, webhook URLs, phone numbers, or destination IDs.

Channel Secrets are strict YAML sequences. Every Target requires a unique `name`; add `notifications: [schedules, salmon-run, gear-dailydrop, gear-regular]` only when that Target should receive a subset. Omit an entire `BOT_*_CONFIG` Secret to disable that adapter.

## S3-compatible publication

`S3_CONFIG` is one strict YAML mapping with `bucket`, `region`, `publicBaseUrl`, and `credentials.accessKeyId` / `credentials.secretAccessKey`. `endpoint`, `forcePathStyle`, `keyPrefix`, and `credentials.sessionToken` are provider-dependent. `publicBaseUrl` must be a credential-free HTTPS bucket-root or CDN URL from which every notification platform can fetch the uploaded images; do not include `keyPrefix` in it.

| Provider | Values needed in `S3_CONFIG` | Official setup | Critical prerequisite |
| --- | --- | --- | --- |
| AWS S3 | `bucket`, real AWS `region`, HTTPS `publicBaseUrl`, dedicated IAM `accessKeyId` / `secretAccessKey`; normally omit `endpoint` and keep `forcePathStyle: false` | [Create a bucket](https://docs.aws.amazon.com/AmazonS3/latest/userguide/GetStartedWithS3.html#creating-bucket) · [Manage access keys](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html) · [Restrict S3 access with CloudFront OAC](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html) | Never use root credentials. Grant only the bucket/object permissions required for publication, and make the resulting object URLs publicly readable—prefer a public HTTPS CDN origin over exposing the bucket itself. |
| Cloudflare R2 | `bucket`, `region: auto`, account endpoint `https://ACCOUNT_ID.r2.cloudflarestorage.com`, R2 API-token Access Key ID / Secret Access Key, and a public custom-domain or `r2.dev` `publicBaseUrl` | [Get started](https://developers.cloudflare.com/r2/get-started/) · [Create R2 API tokens](https://developers.cloudflare.com/r2/api/tokens/) · [Expose a public bucket](https://developers.cloudflare.com/r2/buckets/public-buckets/) | Scope the token to the intended bucket. Cloudflare documents `r2.dev` as non-production; use a custom domain for production delivery and cache control. |
| MinIO / AIStor | `bucket`, server `region`, S3 API `endpoint`, `forcePathStyle: true`, dedicated access key / secret key, and an HTTPS public `publicBaseUrl` | [`mc mb` bucket creation](https://docs.min.io/aistor/reference/cli/mc-mb/) · [Create an access key](https://docs.min.io/aistor/reference/cli/admin/mc-admin-accesskey/mc-admin-accesskey-create/) · [Set anonymous download policy](https://docs.min.io/aistor/reference/cli/mc-anonymous/mc-anonymous-set/) | GitHub-hosted runners must be able to reach `endpoint`; notification platforms must independently reach `publicBaseUrl`. Expose only read access for published objects, preferably through a TLS reverse proxy or CDN. |
| Upyun S3 | `bucket`, `region: us-east-1`, `endpoint: https://s3.api.upyun.com`, `forcePathStyle: true`, an Upyun S3 AccessKey / SecretAccessKey pair, and the public HTTPS acceleration-domain `publicBaseUrl` | [AWS S3 compatibility and credential location](https://help.upyun.com/knowledge-base/aws-s3%E5%85%BC%E5%AE%B9/) · [S3 API reference](https://help.upyun.com/knowledge-base/s3-api/) | Create **S3 access credentials** in the Upyun console rather than reusing the legacy operator/password contract. Upyun does not implement region configuration; the project still requires a non-empty signing-region value. Use HTTPS. |

If signature verification is enabled in Feishu, copy that signing secret into `secret`; always protect the webhook URL. |
| DingTalk | `BOT_DINGTALK_CONFIG`: `name`, `webhookUrl`; optional signing `secret` | [Custom robot access](https://open.dingtalk.com/document/robots/custom-robot-access) | Add the robot to the destination group and select signature-based security when using `secret`. | WhatsApp Cloud API | `BOT_WHATSAPP_CONFIG`: `name`, `accessToken`, numeric `phoneNumberId`, E.164 `recipientPhoneNumber` without `+`, approved `templateName`, `languageCode` | [Cloud API setup](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started) · [Message-template setup](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview) · [Send template messages](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/template-messages) | Use a production-capable token, registered business phone number, billing, and explicit recipient opt-in. | LINE Messaging API | `BOT_LINE_CONFIG`: `name`, `channelAccessToken`, `targetType` (`user`, `group`, or `room`), matching `targetId`; optional `notificationDisabled` | [Create a Messaging API channel](https://developers.line.biz/en/docs/messaging-api/getting-started/) · [Issue a channel access token](https://developers.line.biz/en/docs/basics/channel-access-token/) · [Push-message API](https://developers.line.biz/en/reference/messaging-api/#send-push-message) · [Webhook event source IDs](https://developers.line.biz/en/docs/messaging-api/receiving-messages/#webhook-event-objects) | Obtain user/group/room IDs from webhook events; they must start with `U`, `C`, or `R` respectively. | Slack | `BOT_SLACK_CONFIG`: `name`, `webhookUrl` | [Create and enable an Incoming Webhook](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/) | Install the Slack app to the workspace and authorize the destination channel. Each webhook URL is a secret bound to its installation/channel; the project accepts only official Slack or Slack Gov webhook hosts. |

After saving the Secrets, run **Check Bot Configuration** before any scheduled workflow, then use the side-effecting notification smoke test for each configured destination.
